## Decided
- Objective: a bot, CI job or agent can install codeadd, change providers, features and plugins, and update, from flags alone with stdin not a TTY — never a hang, never a silent guess — while the interactive flow for humans stays exactly as it is. Replaces the 0027B dead end (`cli/src/installer.js:193-202` only throws without a TTY).
- Non-interactive mode is detected, not flagged: `!process.stdin.isTTY` is the switch, the same test 0027B already uses in `installer.js`. No new `--yes` / `--non-interactive` flag — one more flag is one more way to get it wrong.
- Ticket note 3 ("flags: scope … and a yes / non-interactive flag") is superseded: scope stays the existing `--global` / `--user` (`cli/src/cli.js` `resolveTarget`), confirmation is the existing `--force`, and non-interactive mode is the TTY detection above. The board ticket's notes are aligned when it moves to `shaped`.
- Destructive steps are confirmed with the existing `--force` — the vocabulary `uninstall` and `providers remove` already use. Without a TTY and without `--force`, overwriting `.codeadd/` (`installer.js:251`), overwriting a provider dir (`installer.js:260-265`) and removing a provider (`cli/src/modify.js:329-333`) fail with a clear error and change nothing, instead of prompting.
- `install` without a TTY requires `--providers <a,b|none>`; `none` installs the core only. Missing `--providers` exits 1 with a message showing the flag and an example. Provider is the one choice with no safe default for a bot: silently installing `claude` into a Codex project is worse than an error.
- `install` defaults without a TTY: scope `project` (`--global` for user scope); gitignore `true`, the interactive default of `promptGitignore` (`cli/src/prompt.js:141-152`), with `--no-gitignore` to turn it off; features from the `FEATURES` registry defaults (`cli/src/features.js`); plugins none. `--version` / `--channel` keep working as today.
- `modify` gains flags, handled in `cli/src/modify.js` `modify()` (today `void args`): when any of them is present, it builds `desired` and calls the existing `applyDesiredState` — no prompt, no new core. `--providers a,b` is the FINAL provider set (same meaning as on `install`); removing a provider still needs `--force`. Without flags, `modify` is the interactive editor it is today.
- Features and plugins are DELTAS, never final sets: `--enable-feature`, `--disable-feature`, `--enable-plugin`, `--disable-plugin`, each repeatable or comma-separated. A final set would let a bot that only wants `board` switch off `tdd-pipeline` by omission. Names go through the same validation `applyDesiredState` already does (`modify.js` `validate`, feature aliases via `resolveFeatureName`).
- `install` accepts the same four feature/plugin delta flags, applied on top of the registry defaults, so "install with board and gitnexus" is one call. They reuse the same validation as `modify`.
- `install` without a TTY on an existing installation stays an error (0027B behaviour), with the message widened to point at both `codeadd update` and `codeadd modify --…`. No reinstall action flag: a reinstall resets features and plugins (`installer.js` existing-install menu); a bot that really wants it runs `uninstall --force` then `install`.
- A requested plugin whose tool is not detected: warn (the existing `applyDesiredState` / `reportNotDetectedPlugins` wording), keep going, and exit non-zero at the end if any requested plugin was not enabled — the bot needs a machine-readable signal; `plugins enable` already exits 1 in this case (`cli/src/plugins.js`).
- `update` already runs with no prompt (`cli/src/updater.js`); it gets no new flags, only a no-TTY test and docs.
- `codeadd features` / `features list` without a TTY only prints the feature states and exits, like `plugins list` does; today it opens the `promptFeatures` multiselect (`features.js:247-259`) and would wait for input. With a TTY it is unchanged.
- Flag parsing: `getArgValue` in `cli/src/cli.js` has its error hardcoded to `<tag|main>`; generalise the message per flag without changing how `--version` / `--channel` parse. Comma lists and repeated flags are both accepted.
- Docs: the flags go in `USAGE` in `cli/src/cli.js` (what `codeadd --help` prints and `/add-help` Type I reads — the one source a bot can read BEFORE installing) and in `cli/README.md`. `framwork/.codeadd/agent-mode/README.md` gets one short section, "Install and change the installation from a bot", with 3-4 examples and a line that this CLI path works for every provider (the slash-command contract above it stays Claude Code only).
- Layer: all `[product]` (`cli/src/`, `cli/tests/`, `cli/README.md`, `framwork/.codeadd/agent-mode/`).
- Proof, with stdin not a TTY (`spawnSync` with `input: ''` and a timeout, the pattern in `cli/tests/bin-entrypoint.integration.test.js:126-163`; real downloads mocked as in `cli/tests/install.e2e.test.js`): (a) `codeadd install --providers claude,codex --enable-feature board` in an empty dir exits 0 with no prompt, and the manifest has those providers, `board` on and the gitignore block written; (b) `codeadd install` without `--providers` exits 1 with a message naming the flag, and on an existing installation the message points to `update` / `modify`; (c) `codeadd modify --providers claude --force --disable-feature tdd-pipeline` applies the diff with no prompt, and the same call without `--force` exits 1 and changes nothing; (d) `codeadd update` completes with no prompt; (e) `codeadd features list` prints and exits. A requested plugin with no tool detected exits non-zero after the rest is applied. Tests cover install, modify, update and features list; `codeadd --help` and `agent-mode/README.md` list the flags; the interactive flow is unchanged — the existing `install.e2e`, `modify` and `prompt` tests pass untouched.
- Out of scope: `uninstall` when both a project and a global install exist (its scope prompt stays); a `--json` output mode (exit codes and messages are the contract); a reinstall action flag; changing the version through `modify`; the `install --version main` → `vmain` mismatch between `cli/README.md` and `resolveInstallSource`.
