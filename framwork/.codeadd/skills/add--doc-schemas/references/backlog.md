# Project Backlog — Record Format

**This is a format reference, not a doc schema.** Every other file under `references/` describes a Markdown
document an agent authors, with frontmatter, depth floors and a Decision Log. This one describes **two
machine-readable files**: `docs/backlog.jsonl`, one JSON object per line, and `docs/backlog.definitions.json`,
its status vocabulary. **The canonical writer is the backlog Node core.** The local entry
(`.codeadd/scripts/backlog-cli.cjs`) and the publication entry (`.codeadd/scripts/backlog-commit.cjs`) read
and write both files. Local operations need Node >= 22.19.0; publication also needs Git.
Invoke the entries directly with Node — no Bash or WSL bridge.
Neither file has a frontmatter
template, an `id:` under the skill's ID convention, a TL;DR, a depth floor or a Decision Log, because none
of those apply to files a script owns.

The board holds work that is **decided but not started**. That is the gap it fills: the pipeline covers work
about to start, `docs/delivered.jsonl` covers work that is finished, and nothing covered the middle.

## The two files

| File | Holds | Written by | Hand-edited? |
|---|---|---|---|
| `docs/backlog.jsonl` | the tickets, in priority order | the backlog Node entries through the canonical core | never in normal operation |
| `docs/backlog.definitions.json` | the status vocabulary | seeded once by the backlog Node core on the first write | **yes — it is the user's** |

Both are tracked in git, flat directly under `docs/`, UTF-8, **LF**. The location is settled the same way
`docs/delivered.jsonl`'s is: the installer always gitignores `.codeadd/`, and these must survive a fresh
clone. `cli/src/installer.js` never touches `docs/` at all, which is what protects a user's edited
definitions from a reinstall — a structural guarantee rather than a rule someone must remember.

Neither is scaffolded empty. They appear on the first backlog `add`, and their absence means "no ticket
has ever been written", which is information an empty file would destroy.

## Line order is the priority

**The first line is the highest priority.** There is no `rank` field and no `priority` field, deliberately:
an explicit rank means inserting a ticket in the middle rewrites the rank of everything below it, which is
the whole-file rewrite the ordering was meant to avoid.

```
⛔ ONLY `move` REORDERS:
  ⛔ DO NOT: Make `add` take a position — the frequent, cheap write stays a pure append
  ⛔ DO NOT: Reorder as a side effect of `update`, `comment` or `remove`
  ✅ DO: Append at the end, and let `move` be the one mode that rewrites the file
```

A new ticket is the lowest priority until someone moves it. That is not a limitation: capture happens
mid-flow, in the middle of other work, and deciding where a thought ranks is exactly what the person
capturing it does not have the context to do at that moment.

**Every write that is not `move` leaves all other lines byte-identical.** This is the testable form of the
one-line-diff promise, and `.codeadd/scripts/tests/backlog.bats` asserts it directly as
`LINES_BYTE_STABLE` rather than trusting it.

## The ticket

```
{"id":"0007B","title":"cache the provider map","theme":"performance","labels":[],"tldr":"stop re-reading provider-map.json on every artefact","notes":["build.js reads it once per file today"],"done_when":"node scripts/build.js reads provider-map.json exactly once","paths":["scripts/build.js"],"grounded":true,"status":"open","created_at":"2026-09-20T11:04:17Z","updated_at":"2026-09-20T11:04:17Z","comments":[],"work_id":null}
```

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | `[NNNN][L]` with letter `B`, from the **shared global counter**. Generated by the script, never supplied. Never reused, including after a `remove` |
| `title` | yes | One line, what the ticket is |
| `theme` | no | A free grouping label. **There is no registry** — a theme exists because a ticket names it. A second vocabulary file to maintain, for a grouping string, buys nothing |
| `labels` | no | Free tags, one string each. No registry, for the same reason as `theme`. Defaults to `[]`; a value that is not an array is written as `[]`. **`search` does not match them** — they are for filtering, not for finding |
| `tldr` | yes | One line, plain language: what this delivers, not how |
| `notes` | no | The body, one string per bullet. Defaults to `[]` |
| `done_when` | yes | A check someone can actually run. "Fix the review thing" is worthless in three weeks; a named path and a command is worth the trip |
| `paths` | no | The real paths the work touches, from the bounded project check. Defaults to `[]` |
| `grounded` | yes | `true` when the bounded check found real things, `false` when the ticket was recorded as the user stated it. **A reader must be able to tell the two apart** — an ungrounded ticket is still worth keeping, but it has not been checked against the tree |
| `status` | yes | Must be a name defined in `docs/backlog.definitions.json` |
| `created_at` | yes | UTC ISO-8601, second precision. Generated by the script |
| `updated_at` | yes | UTC ISO-8601. Generated by the script, bumped on every write to the line. **`created_at` is never bumped** |
| `comments` | yes | `[{"content": "...", "created_at": "..."}]`, append-only, `[]` when none. A ticket picked up weeks later needs what was learnt since it was written |
| `feature` | yes | The `[NNNN]F` of the feature carrying this ticket, or `null`. Written by `/add-new`, in the **same write** as the status — the feature id is allocated in that step, so the pointer costs no extra commit. **An id, never a path**: `docs/features/0042F-<slug>/` carries a renameable slug and one glob resolves it |
| `work_id` | yes | The `[NNNN][L]` of the work this ticket became — or, in the framework's own repository, the plan basename — or `null`. Filled when the ticket is picked up |

**There is no `scope: internal|product` field.** The framework's own repository has two layers, and a user's
project has one, so a dedicated field would be noise on every ticket there. A grouping only some boards need goes
in `labels` — which is where the framework's own board carries `product`, `internal` or `both`.

**`work_id` is why the ticket's own id is not reused as the work's id.** The counter is global: `0007B` is
spent, and the feature it becomes allocates `0012F` of its own. The two ids stay distinct so a reader can
tell the intent from the work — see `{{skill:add--id-convention/SKILL.md}}`.

⛔ **`feature` and `work_id` are two fields because they answer two questions, and one cannot do both.**

| Field | Answers | Set by |
|---|---|---|
| `feature` | which feature carries this ticket | `/add-new`, as soon as the feature exists |
| `work_id` | that the build started | `/add-build`, with `doing`, in one write |

**`work_id` is what the pipeline's phase logic reads.** Setting it as early as `/add-new` would make the
pipeline treat the build as started and stop `/add-plan` writing its own phase — the planning phase would
vanish from the board. That is why the pointer needed a field of its own rather than an earlier `work_id`,
and it is the reason a later reader must not merge them.

## The definitions file

```json
{
  "columns": [
    { "name": "backlog",  "order": 1, "label": "Backlog"  },
    { "name": "shaping",  "order": 2, "label": "Shaping"  },
    { "name": "planning", "order": 3, "label": "Planning" },
    { "name": "building", "order": 4, "label": "Building" },
    { "name": "review",   "order": 5, "label": "Review"   },
    { "name": "done",     "order": 6, "label": "Done"     },
    { "name": "dropped",  "order": 7, "label": "Dropped", "hidden": true }
  ],
  "statuses": [
    { "name": "open",      "order": 1, "column": "backlog",  "label": "Open",      "means": "decided, nobody picked it up" },
    { "name": "refining",  "order": 2, "column": "shaping",  "label": "Refining",  "means": "add-brainstorm or add-new running" },
    { "name": "shaped",    "order": 3, "column": "shaping",  "label": "Shaped",    "means": "about.md exists, waiting to plan" },
    { "name": "planning",  "order": 4, "column": "planning", "label": "Planning",  "means": "add-plan running" },
    { "name": "planned",   "order": 5, "column": "planning", "label": "Planned",   "means": "plan approved, waiting to build" },
    { "name": "doing",     "order": 6, "column": "building", "label": "Doing",     "means": "add-build running" },
    { "name": "in-review", "order": 7, "column": "review",   "label": "In review", "means": "build finished, PR may not exist yet; waiting for review and merge" },
    { "name": "done",      "order": 8, "column": "done",     "label": "Done",      "means": "delivered" },
    { "name": "dropped",   "order": 9, "column": "dropped",  "label": "Dropped",   "means": "decided against" }
  ]
}
```

Written once, on the first WRITE that finds it absent — a read never brings a file into existence. **Never rewritten after that**,
and `backlog.bats` asserts it with `DEFS_PRESERVED`: a hand-edited file survives further writes
byte-for-byte.

⛔ **The SEEDED SHAPE grew; the never-rewritten promise did not change.** The shape above replaced a
four-status one, and a reader meeting both facts at once can easily conclude the script now updates an
existing file. It does not, and `DEFS_PRESERVED` is unmodified. **Nothing reconciles an old file with this
shape — not a migration, not a fill-in, not on a write.** A project whose file predates the change keeps it
exactly as it is, and a write naming a status it does not define is refused, as any undefined status always
was.

### Three of the keys are new, and all three are optional

| Key | On | When absent |
|---|---|---|
| `column` | a status | falls back to the status's own `name` |
| `label` | a status | falls back to the status's own `name` |
| `hidden` | a column | `false` |
| `columns` | the top level | derived from the statuses, in `order` order |

**The seeded shape above carries all of them explicitly**, so a fresh project never exercises a fallback.
The fallbacks exist for a file someone hand-edits and leaves a key out of — and they are resolved by
**whoever reads the file for display**, not by the backlog Node core, which reads a status name and nothing else.

### The nine names are a contract, not a mechanism

`open`, `refining`, `shaped`, `planning`, `planned`, `doing`, `in-review`, `done`, `dropped` are the names
the pipeline writes. **Nothing enforces them.** Rename one and every write naming it is refused with
`REFUSED=unknown-status` — one refusal per write, each reported, the command continuing. That is loud, and
it is the user's own edit.

**Two statuses share a column wherever a phase has a running state and a parked one** — `refining`/`shaped`
and `planning`/`planned`. That pairing is what lets seven columns hold nine statuses, and it is what makes
`column` worth having at all.

```
⛔ THE VOCABULARY IS THE USER'S WORKFLOW, NOT THE FRAMEWORK'S:
  ⛔ DO NOT: Re-seed the file because its statuses are not the shipped nine
  ⛔ DO NOT: Add a status to it on the user's behalf, reserved or otherwise
  ⛔ DO NOT: Refuse to READ a board because the file no longer defines a status in use
  ✅ DO: Create it when absent, validate writes against it, and report what it no longer covers
```

**`order` is a sort key and never a meaning.** It is NOT the ticket's priority — that is line order in the
JSONL. With columns in play it sorts **twice over, at two levels**: a status's `order` sorts it within its
own column, and a column's `order` sorts the columns. Neither says anything about phase, direction or what
comes next.

```
⛔ NOTHING READS order AS A POSITION IN THE FLOW:
  ⛔ DO NOT: Treat `order: 6` as "further along" than `order: 4`
  ⛔ DO NOT: Derive a phase, a transition or a next step from it
  ✅ DO: Read a status by its NAME — the moment a user reorders their statuses, any rule built on
         `order` is wrong and nothing reports it
```

**A definitions file the script does not enforce is decoration**, which is why a write carrying an
undefined status is refused. But refusing to *read* would lock a user out of their own board over an edit
they are entitled to make, so the two directions differ:

| Direction | An undefined status |
|---|---|
| **write** — `add`, `update` | Refused: exit 2, `REFUSED=unknown-status`, the board unchanged |
| **read** — `list`, `search`, `get` | Reported as `UNDEFINED_STATUS=<name>`, exit 0, every ticket still returned |

## Reading rules

- **A damaged line is reported by its number and skipped.** `DAMAGED_LINES=<n>` gives the count and one
  `DAMAGED_LINE=<n>` line gives each number; every other ticket still answers and the exit stays 0. A
  hand-edited board is expected, not an anomaly — the delivery index's own reader already treats a damaged
  line this way, and `references/delivery-index.md` states it there.
- **The allocators read this file, and how they read it is owned by `{{skill:add--id-convention/SKILL.md}}`**
  — see its "One counter, two sources, two implementations" section. What matters here is only the
  consequence for the format: a ticket's id must stay recoverable from the raw text of its line, which is
  why `id` is written first and is never omitted.
- **`list` defaults to open tickets.** `--all` returns every one, `--status <name>` filters to one.
  `--full` restores the raw rows; `--ids` emits just the identities, filter and order preserved.
- **`search` matches `title`, `tldr` and `notes`**, and returns in board order — priority order survives
  the filter. **It answers all statuses** (so a target in flight is never hidden), also matches an
  exact ticket id case-insensitively, and takes only one literal query plus an optional `--full`.
- **`get <id>` is the detail read.** An exact, case-sensitive lookup with no status filter that returns
  the raw row: notes, paths, `done_when` and `work_id` come from `get`, never from a summary. Exit 0 with
  `TICKETS_RETURNED=0` on an unknown id or absent board — a result, not a refusal; `get` with no id is
  `ERROR=missing-id`, exit 2.
- **`list` and `search` print a seven-field summary.** Exactly `id, status, title, tldr, theme, labels,
  updated_at`, in that order; the `tldr` is a preview cut at 120 code points (`…` when cut), without
  splitting surrogate pairs. The projection is presentation only: nothing is rewritten, and the board
  export and the board API keep the complete records.
- **Output is `KEY=VALUE` metadata, then payload lines.** A line starting with `{` is a ticket; anything
  else is a key; `--ids` emits one id per line instead. This is the same shape `delivered.cjs` emits, so
  one consumer parses both.

| Key | On | Means |
|---|---|---|
| `BACKLOG_PRESENT` | every read | `yes` or `no` — an absent board is a result, not a failure |
| `TICKETS_TOTAL` | every read | Tickets on the board, before any filter |
| `TICKETS_RETURNED` | every read | Tickets after the filter |
| `DAMAGED_LINES` | every read | How many lines failed to parse |
| `DAMAGED_LINE` | per damaged line | Its 1-based line number |
| `UNDEFINED_STATUS` | per such status | A status in use that the definitions no longer define |
| `READ_VIEW` | every read | `summary`, `full` or `ids` — which projection the payload carries |
| `STATUS_COUNTS` | every read | One JSON object counting the whole board before any filter, statuses in first-occurrence order |
| `TICKET_ID` | every write | The id written, allocated or targeted |

## Hard bans

Each is testable, and each has a `REFUSED=` name below.

1. **`id` is generated, never supplied.** A caller that sends one is refused. The id comes from the shared
   counter, and letting a caller pick one is how two tickets end up sharing a number.
2. **`created_at` and `updated_at` are generated, never supplied.** Same reason `log-jsonl.cjs` generates
   its own timestamp: a caller-supplied time is a time nobody can trust.
3. **`status` must be defined in `docs/backlog.definitions.json`.** On writes only — see the table above.
4. **An id already on the board is never added twice.** One line per ticket, always.
5. **`title`, `tldr` and `done_when` are required and non-empty.** A ticket without a runnable check is the
   entry that is worthless in three weeks, which is the failure this whole file exists to prevent.
6. **The record must be exactly one JSON object** for `add`, `update` and `comment`.
   Agents pass `--record-file <path>`; the Node entries also accept stdin when that option is absent.
7. **An id named by `update`, `comment`, `move` or `remove` must be on the board.** Including the anchor of
   `move --after`.

Two further promises are structural rather than submittable, so they carry no `REFUSED=` name:
**the local CLI never commits**, and **`docs/backlog.definitions.json` is never rewritten once it exists**.
The publication entry owns Git commits. Native CLI tests prove the local no-process boundary;
`backlog.bats` proves definitions preservation.

## `REFUSED=` vocabulary

A record breaking a hard ban is caller error in the same sense a bad mode is: the write exits **2** and
prints `REFUSED=<name>`. The names are the machine-readable contract — a consumer branches on them, so they
are listed here rather than left implicit in the script.

`backlog.bats` L1.4 asserts that every `REFUSED=` string the script can emit appears in this table, so the
two cannot drift.

| `REFUSED=` | Ban | The caller did this |
|---|---|---|
| `invalid-json` | 6 | the record was not one parseable JSON object |
| `missing-field` | 5 | `title`, `tldr` or `done_when` is absent or empty |
| `reserved-field` | 1, 2 | the record carried `id`, `created_at` or `updated_at` |
| `unknown-status` | 3 | `status` is not a name in the definitions file |
| `duplicate-id` | 4 | the id is already on the board |
| `unknown-id` | 7 | the id named is not on the board, including a `move --after` anchor |

The name is shared with `delivery-index.md` where the meaning is the same: `invalid-json` and
`missing-field` mean there exactly what they mean here. One spelling across both logs is what lets a
consumer branch once.

## Exit codes

The backlog follows the script family's three-code doctrine, with the same single departure
`delivered.cjs` makes — and it is the backlog Node core that owns it, through every entry: the local
`backlog-cli.cjs` and the publication `backlog-commit.cjs`.

| Exit | Means |
|---|---|
| `0` | A probe result, whatever it says. `list` and `search` always exit 0, **including on an absent board** |
| `1` | **The filesystem refused a write.** The departure: the always-0 rule governs probe *results*, and a ticket that silently fails to land is the one case where exit 0 would be a lie |
| `2` | Caller error — a bad mode, bad arguments or a hard ban (`REFUSED=<name>`) |

**Exit-2 causes are distinguished by output, not by code.** If Node itself is unavailable, the host
reports the launch failure; the Node entries cannot emit a runtime-missing diagnostic before startup.
